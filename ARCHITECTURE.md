# Архитектура Siberian Livecoding

Этот файл — актуальная карта проекта. Обновляйте его при добавлении нового сервиса, крупной сущности, маршрута, способа авторизации или инфраструктурного компонента.

## 1. Назначение проекта

Siberian Livecoding — учебная платформа, в которой:

- учитель создаёт группы и закрытый код регистрации;
- ученик регистрируется, один раз выбирает группу и получает назначенные задания;
- задание назначается группе и/или конкретным ученикам и может быть скрыто;
- поддерживаются задания с автопроверкой и проверкой кода;
- учитель и ученик могут одновременно редактировать один документ в режиме live coding;
- учитель следит за прогрессом, комментирует строки кода и выставляет оценку;
- production-сайт может быть закрыт клиентскими сертификатами доверенных компьютеров.

## 2. Общая схема

```text
Браузер
  │
  ├── HTTP /api/* ───────────────► FastAPI ─────────► PostgreSQL
  │                                  │
  │                                  └── JWT в HttpOnly cookie
  │
  ├── WebSocket /collab ─────────► Hocuspocus/Yjs ─► PostgreSQL
  │                                      │
  │                                      └──────────► Redis
  │
  └── HTML/CSS/JS ───────────────► React/Vite

Production: браузер ─► Caddy (TLS + mTLS) ─► frontend/backend/realtime
Development: браузер ─► Vite proxy ─────────► backend/realtime
```

### Основные группы API

| Префикс | Назначение |
| --- | --- |
| `/auth/*` | `student-register`, `student-login`, `teacher-login`, `logout` |
| `/student/*` | Доступные группы, профиль и первичный выбор группы |
| `/tasks/*` | Доступные ученику задания, ответ, код и комментарии |
| `/admin/groups*` | CRUD групп учителя |
| `/admin/students*` | Список учеников и смена группы учителем |
| `/admin/registration-code*` | Просмотр и смена закрытого кода регистрации |
| `/admin/tasks*` | Создание, видимость, редактирование, удаление, прогресс и ревью |
| `/admin/tests*` | Старый/совместимый слой сущности тестов; новые задания могут жить без `test_id` |
| `/health` | Проверка доступности backend |
| `/teams/*` | Командные сессии, команды, доски и карточки с проверкой роли участника |

Frontend всегда обращается к API через `/api`. В `frontend/src/utils/api.ts` этот префикс добавляется автоматически. Vite и Caddy снимают `/api` перед передачей запроса FastAPI. Другие URL, включая `/student/*`, принадлежат React Router и должны попадать во frontend SPA. Это одновременно предотвращает возврат `index.html` вместо API JSON и конфликт клиентских маршрутов с backend.

## 5. Модель данных

### Пользователи и группы

- `Teacher` — email, хеш пароля, закрытый код регистрации.
- `Student` — ФИО, уникальный логин, хеш пароля, текущая группа и учитель регистрации.
- `StudentGroup` — принадлежит одному учителю; название уникально внутри учителя.
- Учитель может менять группу ученика. Сам ученик выбирает её только при первичном входе.

### Задания

- `Task` — базовая сущность: создатель, название, описание, тип, видимость и порядок.
- `task_group_assignment` — назначение задания группам.
- `task_student_assignment` — назначение задания конкретным ученикам.
- Ученик видит только опубликованное задание, назначенное лично ему или его группе.
- `AutoCheckTask` — способ проверки (`exact`, `regex`, `tokenized`) и ожидаемое значение.
- `CodeReviewTask` — исходный код, язык и режим ученика (`review` или `live`).

### Работа ученика

- `Submission` — попытка ответа на автопроверяемое задание.
- `StudentCodeSession` — отдельная копия кода ученика, текст и бинарное состояние Yjs. Пара `task_id + student_id` уникальна.
- `CodeComment` — комментарий ученика или учителя к номеру строки.
- `Grade` — балл и комментарий учителя.

### Командная работа

- `TeamSession` — отдельная командная практика внутри учебной группы.
- `Team` и `team_membership` — временная команда и её участники; ученик может состоять только в одной команде конкретной сессии.
- `KanbanBoard` — отдельная доска команды.
- `KanbanColumn` — упорядоченная колонка; при создании команды добавляются «Идеи», «Нужно сделать», «В работе» и «Готово».
- `KanbanCard` — карточка с заголовком, описанием, приоритетом, позицией, необязательным ответственным и учеником-автором идеи. Для карточек учителя автор остаётся пустым.

### Legacy-слой

- `Test` и `student_test` остались для совместимости с ранней моделью входа по коду теста.
- Текущая основная модель выдачи заданий строится вокруг `Task`, групп и конкретных учеников.
- Не добавляйте новую функциональность в `Test`, если она не нужна для обратной совместимости.

## 7. Совместное редактирование

`realtime/src/server.js` запускает Hocuspocus server.

1. Комната имеет строгое имя `task-{taskId}-student-{studentId}`.
2. Браузер подключается к `/collab` и передаёт существующую JWT cookie.
3. Realtime-сервис проверяет JWT и назначение задания напрямую в PostgreSQL.
4. Учитель допускается только к собственному заданию.
5. Ученик допускается только в свою комнату и только к видимому заданию.
6. В режиме `review` соединение ученика переводится в read-only; в режиме `live` он может редактировать.
7. Yjs разрешает конкурентные изменения без ручного объединения текста.
8. Redis распространяет обновления и presence между экземплярами realtime.
9. PostgreSQL хранит обычный `source_code` и полное бинарное `ydoc_state`.

Важно: в collaborative-режиме единственный источник истины в редакторе — `Y.Text`. Нельзя периодически заменять его кодом из REST-ответа: это создаёт конкурирующую транзакцию и может дублировать текст.

## 8. Авторизация и безопасность

- Пароли хешируются backend-сервисом и не хранятся открытым текстом.
- JWT записывается в HttpOnly cookie `token` и по умолчанию действует 90 минут (`ACCESS_TOKEN_EXPIRE_MINUTES`).
- Общий frontend-клиент `apiFetch` при `401 Unauthorized` очищает локальное состояние входа и перенаправляет пользователя на соответствующую страницу авторизации.
- Backend проверяет роль (`teacher`/`student`) и владение сущностями.
- Регистрация ученика требует действующий код конкретного учителя.
- Смена кода сразу запрещает регистрации по старому коду, но не влияет на готовые аккаунты.
- Секреты должны находиться только в `.env` на соответствующей машине.

## 9. Доверенные компьютеры и mTLS

`device-access/` содержит серверные и Windows-скрипты жизненного цикла сертификатов.

- Windows-компьютер создаёт приватный ключ и CSR.
- Серверный CA подписывает CSR.
- Сертификат устанавливается на тот же компьютер вместе с приватным ключом.
- `rebuild-trust.sh` формирует trust bundle активных устройств.
- `activate.sh` включает обязательную проверку клиентского сертификата в Caddy.
- `revoke-device.sh` отзывает доступ конкретного устройства.

Приватный CA и выданные сертификаты сервера хранятся вне Git в `/opt/testing-platform-device-ca`. Сгенерированные runtime-файлы Caddy находятся в `runtime/device-access` на сервере и подключаются через import в `Caddyfile`.

mTLS ограничивает доступ к приложению, но сам по себе не заменяет внешний DDoS-фильтр.

## 10. Docker и сети

### Development

`docker-compose.yml` запускает:

- `frontend:5173` — Vite с hot reload;
- `backend:8000` — Uvicorn с reload;
- `realtime:1234` — WebSocket-сервис;
- `postgres:5432` — база данных;
- `redis:6379` — внутренний Redis.

### Production

`docker-compose.prod.yml` запускает те же сервисы без dev-mount и добавляет Caddy на портах 80/443. Frontend собирается и раздаётся через Nginx внутри контейнера; Caddy остаётся публичной точкой входа.

Маршрутизация Caddy:

- `/collab*` → realtime;
- `/api/*` → backend со снятием `/api`;
- всё остальное → frontend SPA.

## 11. Миграции и команды

```bash
# Локальный запуск
docker compose up -d --build

# Миграции
docker compose exec backend alembic upgrade head

# Создание учителя
docker compose exec backend python -m app.scripts.create_teacher \
  --email admin@example.com --password change-me

# Проверка frontend
cd frontend
npx tsc -p tsconfig.app.json --noEmit --incremental false
npx vite build --configLoader runner

# Backend-тесты
cd backend
pytest
```

## 12. Правила развития проекта

1. Новую таблицу или колонку оформлять Alembic-миграцией; `create_all` в приложении не использовать.
2. Новые запросы frontend выполнять через `apiFetch`, а не через прямой `fetch`.
3. Любой admin endpoint обязан проверять роль учителя и владение сущностью.
4. Любой student endpoint обязан проверять назначение и видимость задания.
5. Пользовательский текст добавлять сразу на русском и английском через `useTranslation`; русский — основной язык.
6. Цвета интерфейса брать из theme tokens, не задавать локальные палитры в компонентах.
7. Изменения CodeMirror проверять как в обычном, так и в collaborative-режиме.
8. Не коммитить `.env`, ключи, приватный CA, выданные приватные ключи, дампы БД и runtime-сертификаты.
9. При изменении сервисов, маршрутов или моделей обновлять этот файл.

## 13. Известные архитектурные особенности

- Сущность `Test` является legacy-слоем; основной пользовательский сценарий уже работает через самостоятельные `Task`.
- В frontend ещё есть крупные страницы с локальным состоянием. При дальнейшем росте стоит выделить API hooks и доменные типы из page-компонентов.
- Тексты локализации сейчас задаются парой `t(ru, en)` рядом с компонентом. Если языков станет больше двух, нужно перейти на словари с ключами.
- REST polling используется для части данных прогресса и комментариев; сам текст кода синхронизируется через WebSocket/Yjs.
- Предупреждение Vite о крупном bundle пока не блокирует сборку; будущая оптимизация — ленивые маршруты и отдельный chunk для CodeMirror/Yjs.
